Architecture Overview

OUR FRAUD PREVENTION LAYERS

01 // LAYER

DEVICE ID CAPPING

Enforces strict account registration ceilings (e.g. max 2 accounts) per mobile device instance to stop endless account cycling.

Target: Infinite local account creation
02 // LAYER

DRM ID CAPPING

Extracts immutable Widevine DRM hardware root identity. Resists app uninstalls, dual-space clones, and simple rooting resets.

Target: App-cloners & soft identity resets
03 // LAYER

HMAC SIGNING

Signs every sensitive API request with timestamp & unique nonce. Backend rejects replays, postman scripts, and tampered parameters.

Target: Direct script/cURL attacks & replays
04 // LAYER

APP INTEGRITY

Leverages Google Play Integrity & Apple App Attest APIs to cryptographically attest official binary origin and legitimate OS environment.

Target: Modified APKs, sideloads, and emulators
STRATEGIC IMPACT:

Multiple signals → Multiple validation points → Exponentially higher resistance to coordinated abuse.

Defense Layer 02

LAYER 2 — WE NEEDED A STRONGER DEVICE SIGNAL

VULNERABILITY OF SIMPLE DEVICE ID

  • ✕ App Uninstalls: Resetting app storage may regenerate GUID on newer OS.
  • ✕ Dual Space / Cloners: Virtual sandboxes mask and synthesize fake Device IDs.
  • ✕ Root Hooks: Xposed/Frida can easily overwrite getAndroidId() in memory.
🔐

THE STRONGER SIGNAL: DRM ID

Extracted via Android's MediaDrm Widevine security module. Tied to tamper-resistant hardware cryptographic keys.

Persists across app reinstallations & dual-app sandboxes.
SECURITY EVOLUTION:

When software-level IDs can be regenerated, security must anchor to hardware-backed identity.

Dual Signal Architecture

TWO SIGNALS ARE STRONGER THAN ONE

CLIENT MOBILE DEVICE RUNTIME
SIGNAL A
DEVICE ID

Broad compatibility across 100% of platforms.

SIGNAL B
DRM ID

Hardware-anchored Widevine identifier.

↓ Dual Transmission via Secure Request Body ↓
BACKEND HYBRID VALIDATION RULE

If DRM ID matches an existing capped device, request is BLOCKED even if Device ID was spoofed or randomized!

KEY PRINCIPLE:

The backend validates device identity signals together instead of placing fragile trust in Device ID alone.

Engineering Trade-Offs

SECURITY VS. COMPATIBILITY

LEGACY DEVICES (ANDROID 8 & OLDER)

INCOMPATIBLE
✕ MediaDrm.PROPERTY_DEVICE_UNIQUE_ID unavailable
Older Android API levels crash or return empty byte arrays.
Cannot mandate DRM ID as strict universal blocker.

MODERN DEVICES (ANDROID 9+)

FULL SUPPORT
✓ Hardware MediaDRM Widevine standard
Reliable 32-byte unique cryptographic hardware signature.
Covers ~94% of active production ecosystem.
OUR ARCHITECTURAL SOLUTION: Device ID guarantees 100% universal baseline coverage, while DRM ID provides deep hardware defense wherever available.
SECURITY RULE:

DRM ID could not be used as the exclusive signal, but acted as a resilient progressive enhancement.

Cryptographic Defense

LAYER 3 — HMAC REQUEST SIGNING

SIGNING MATERIAL
App Secret / Key
FRESHNESS
Timestamp (Unix)
UNIQUENESS
Random Nonce
HASH-BASED MESSAGE AUTHENTICATION CODE (SHA-256)
HMAC = SHA256( Key, Payload + Timestamp + Nonce )
Client Sends Signature → Backend Recomputes & Verifies
HMAC GUARANTEE:

Protects API payloads from in-transit tampering, direct unauthenticated API execution, and replay attacks.

Threat Mitigation Scope

WHAT ARE WE TRYING TO PREVENT?

THREAT 01

DIRECT API SCRIPTS

Attackers invoking backend loyalty endpoints directly without launching the Android/iOS application binary.

Neutralized by: Missing Signature
THREAT 02

REPLAY ATTACKS

Capturing a valid historical redemption request through a proxy and re-transmitting it multiple times.

Neutralized by: Nonce + Timestamp
THREAT 03

LEGACY / BROKEN BUILDS

Targeting obsolete API endpoints that lacked security validations by executing old client builds.

Neutralized by: Gateway Policy
CRITICAL TAKEAWAY:

The goal is to make every sensitive API request require valid, fresh request authentication.

End-to-End Sequence

ONE REQUEST, ONE VALIDATION

CLIENT APP EXECUTION
1. Assemble JSON request payload
2. Fetch UTC Unix Epoch timestamp
3. Generate cryptographically random Nonce (UUIDv4)
4. Compute HMAC signature using signing material
5. Attach X-Signature, X-Timestamp, X-Nonce headers
BACKEND GATEWAY VERIFICATION
1. Check Timestamp: |Current - Header| < 30 seconds?
2. Check Redis: Has Nonce been seen within TTL window?
3. Recalculate signature with server signing material
4. Constant-time compare client vs computed signature
5. ACCEPT request & record Nonce in Redis cache
Technical Reality: In mobile architectures, signing materials embedded in client binaries can eventually be reverse engineered with enough effort. HMAC raises the attack difficulty barrier from trivial script automation to dedicated reverse engineering.
GATEWAY PROTOCOL:

If timestamp skew exceeds 30 seconds, nonce is repeated, or signature fails by a single bit → immediate 401 Unauthorized.

Verification Scope

HOW DID WE TEST HMAC?

✓ VALID HAPPY PATHS

  • ✓ Valid signature computed with standard key
  • ✓ Fresh timestamp within ±30s window
  • ✓ Cryptographically unique UUID nonce
  • EXPECTED: HTTP 200 OK

✕ NEGATIVE ATTACK PATHS

  • ✕ Missing X-Signature header
  • ✕ Corrupted / bit-flipped signature string
  • ✕ Stale timestamp (>30s historical or in future)
  • ✕ Replayed nonce within TTL cache window
  • EXPECTED: HTTP 401 REJECTED

Debate & Decision

SHOULD WE DISABLE FRAUD CONTROLS IN QA?

OPTION A (THE EASY TRAP)

DISABLE CONTROLS IN STAGING

✓ QA is fast and hassle-free.

✓ Automated emulators run without blocks.

FATAL FLAW: Staging behavior ≠ Production behavior. Security regressions slip directly into release!
OPTION B (OUR CHOSEN PATH)

KEEP ALL CONTROLS ENABLED

✓ QA tests identical security rules as real users.

✓ Attacker bypasses caught before release.

SOLUTION: Introduced automated backend reset pipelines to recycle blocked test devices smoothly.
STRATEGIC DECISION:

We kept all security controls strictly active in QA, accepting higher data-management complexity to guarantee parity.

WHAT WE LEARNED

01 Behavior can reveal fraud long before technical investigations pinpoint the code.
02 One security mechanism is never enough; defense-in-depth is the only resilient model.
03 Security controls must be tested as live attack surfaces, not static pass/fail checkboxes.
04 Fraud prevention inevitably forces QA to evolve into test-data and state engineering.
05 Fraud prevention requires continuous investigation and rapid adversarial adaptation.
ORGANIZATIONAL CULTURE:

Security is a shared discipline across product management, backend development, and QA testing.

Engineering Value

QA'S ROLE IN FRAUD PREVENTION

📋

PRODUCT

Defines business boundaries, promotional economics, and acceptable user friction thresholds.

⚙️

BACKEND

Implements high-throughput cryptographic verification, redis counters, and audit logging.

🛡️

QA ENGINEERING

Constructs adversarial environments, simulates attacker tooling, audits bypasses, and verifies telemetry accuracy.

KEY PERSPECTIVE:

QA is not merely checking off tickets to verify that a feature exists. QA challenges the security layer directly from the determined attacker's vantage point.

Philosophical Shift

FROM "DOES IT WORK?" → "CAN IT BE ABUSED?"

FRAUD PREVENTION QA
Feature + Economic Incentive Identified
↓
How can this protocol be bypassed?
↓
What happens when headers or payloads are manipulated?
↓
What occurs completely outside the official client?
↓
Verdict: RESILIENT / EXPLOITABLE
TAKEAWAY:

Security testing requires rigorously thinking far outside the boundaries of the happy path.
